# CLAUDE.md

chimimouryou: a fork of [ttu-ttu/ebook-reader](https://github.com/ttu-ttu/ebook-reader) (ッツ Ebook Reader), a browser-based EPUB/HTMLZ reader aimed at Japanese text, extended into a self-hosted reader for a Calibre library: accounts, sync, highlights, AI helpers, manga, difficulty estimates. It runs on any server with Docker (`docker-compose.yml`, guide in `docs/INSTALL.md`).

The details of a particular deployment (hosts, addresses, how it is deployed and rolled back) are in `CLAUDE.local.md` when present; it is not in git.

## Repository layout

- pnpm workspace: the only app is `apps/web`, a SvelteKit app built with `@sveltejs/adapter-static`.
  The output is purely static; there is no server-side code at runtime.
- `apps/web/src/routes/`: pages. `b/` is the reader (`b/+page.svelte` is large), `m/` the manga reader, plus `manage/` (library), `settings/`, `statistics/` and `auth/`.
- `apps/web/src/lib/components/`: UI components. `book-reader/` is the reading view and `settings/` is the settings UI.
- `apps/web/src/lib/data/`: stores, settings enums and storage/database code. Books live in the browser (IndexedDB), synced with the server (Calibre source) or GDrive/OneDrive.
- `apps/web/src/lib/functions/`: parsing, file loaders and utilities.
- `scripts/calibre/`: the server side: nginx template, catalog builder and Python services (accounts, import, difficulty) with their tests.
- `docker/`, `docker-compose.yml`: the Docker install. `docker-compose.static.yml` is upstream's reader-only image.
- `scripts/deploy.sh`: deploys the working tree to a server (Proxmox container, SSH or local) and restarts the stack; reads the gitignored `local/` (`deploy.env`, `env`, optional override). `deploy/server/` holds the commands it installs (`ebook-compose`, `ebook-account`, `ebook-update`), `deploy/examples/` optional setups (`tailscale-https/`).
- Styling: Tailwind 3 + SCSS. Svelte 4 syntax in app code (not runes).

## Git workflow

- The fork's branch is `main` on GitHub; upstream is the `upstream` remote. Internal names (`ebook-reader` compose project, `/opt/ebook-reader`, `ttu-reader-data` sync root, `ttu_session` cookies) predate the name and stay: changing them would break existing installs.
- To pull upstream updates: `git fetch upstream && git merge upstream/main`.
- Commit with clear messages (`feat:`, `fix:`, `docs:` …) so changes are easy to rebase or merge against upstream.

## Server

- Docker stack (`docker-compose.yml`): `web` (nginx + the built app; `docker/40-ebook-reader.sh` creates `/data` for PUID/PGID, sets the nginx user and renders the nginx template), `account` and `catalog` (services image target `base`), and the optional profiles `import` and `difficulty`. Paths come from the environment (`/library`, `/data/{sync,accounts,state}`); every setting is in `docs/CONFIGURATION.md`.
- nginx config: `scripts/calibre/nginx-ebook-reader.conf.template` (upstream's `default.conf` plus the Calibre and account locations), rendered by `render-nginx.sh` when the web container starts. Server-level extras (TLS, resolver, real IP) go in `/etc/nginx/ebook-reader.d/`.
- `DATA_PATH` holds everything the server stores: `sync/` (shared WebDAV folder, `/calibre/sync/`), `accounts/<account id>/` (per-account WebDAV, `/account/sync/`), `state/account/accounts.db`, `state/catalog/` (catalog, `no-cover.json`), `state/import/` (queue, `jobs.json`, `calibre-write.lock`), `state/difficulty/` (results, `frequency-dictionary.zip`). Account data includes synced AI keys: never put `DATA_PATH` on storage other machines can read.
- Browser storage (settings, cached books, highlights) is per origin, so an HTTP and an HTTPS address of the same server don't share it. Calibre books and their progress, statistics and highlights come back from the server. Over plain HTTP the service worker/offline mode and some File System Access features don't work.

## Features (not upstream)

- Calibre library (`/calibre/catalog.json`, files at `/calibre/library/`, read-only; only book files and covers are served).
  The catalog is built from a copy of `metadata.db` by `build-catalog.py` (the `catalog` service, every `CATALOG_INTERVAL` seconds, only when the DB changed).
- Calibre is the default storage source (`StorageKey.CALIBRE`, `lib/data/storage/handler/calibre-handler.ts`).
  The library lists the whole catalog. Opening a book for the first time downloads it from Calibre, processes it, and uploads the processed data to the server.
  Reader data (book data, progress, statistics) syncs through nginx WebDAV at `/calibre/sync/`, with the same folder-per-title layout as GDrive. Sync for Calibre books is always on, regardless of the auto-replication setting.
  Books are identified by title, so the catalog makes duplicate Calibre titles unique by appending ` (author)` or ` [id]`.
  Importing a file into the Calibre source adds it to the Calibre library (accounts with the `import` permission): `lib/data/calibre-import.ts` uploads to `/calibre/import/api/` (`scripts/calibre/import/service.py`), a queue that runs `calibredb add` one book at a time and then rebuilds the catalog. It is the only writer of `metadata.db`; Calibre's own title+author check refuses duplicates. Afterwards the library is refreshed and books whose title names an existing series are offered for it. `build-catalog.py` takes a lock (`catalog.json.lock`) and gives `catalog.json` its inputs' mtime, so builds from the timer and the queue don't race.
  Series made by readers (library select mode → "Make series", `book-card/series-dialog.svelte`, `lib/data/series-overrides.ts`, `series` permission) are shared by everyone in `/calibre/sync/series.json`, keyed by title; they override the catalog's series (an empty series removes a book from one) and are applied in `CalibreStorageHandler.getBookList`.
  Calibre books are cached in the browser (IndexedDB) and only re-downloaded when the server copy is newer. The "External Read" hint is skipped for them.
  Books without a Calibre cover get one: the catalog builder extracts it from the EPUB into the book's folder as `cover.jpg` (JPEG unchanged, other formats converted at full size; never overwrites; `metadata.db` is not modified, so Calibre's `has_cover` stays unset). Cover detection: OPF cover-image / `meta name=cover` / guide cover page / item named "cover" / first image on the first pages / first manifest image; SVG/XHTML cover pages are followed to their image. EPUBs without a usable one are remembered in `state/catalog/no-cover.json` (raise `COVER_EXTRACTOR_VERSION` to retry them). The builder must run as the library owner (`PUID`).
  The catalog skips non-zip EPUBs, such as macOS `._` resource forks that were imported into Calibre.
  It also carries tags, rating and publisher, and a series for every book: Calibre's own series, or one inferred from volume numbers in titles (`split_volume` in `build-catalog.py`, `seriesInferred: true`).
  `scripts/calibre/assign-series.py` writes such series into Calibre itself (in the `import` container: `docker compose exec import calibre-debug -e /app/assign-series.py -- [--apply]`), using the same title parsing: books without a series join a matching Calibre series (width/case ignored) or, two or more distinct volumes with a common author, form a new one; books by another author (e.g. manga adaptations) are left out. It also merges series that are one work (`merge_plan`, sharing an author): names that differ only in width, case, spaces, punctuation or store tags like 【電子版限定特典付き】 (`merge_key`, letters and digits only; the spelling found in most book titles wins), and series named after one volume (`volume_series`: digits only, not 上/中/下; a misnamed main series keeps its indexes, per-volume part series get N.part, sequels like はやて×ブレード2 stay apart). Store tags are also left out of new series names. Dry run by default; `--apply` copies `metadata.db` to `state/import/backups/` (last 5) and writes through Calibre's API under the import queue's lock; `--json` for machines. Admin panel → Tools → Series runs it through the import service (`POST /calibre/import/api/series`, admins only via nginx `/_account_admin`, `components/admin/series-tool.svelte`).
- Reader extras:
  - "Listen" (headphones icon, `book-reader/listen-panel.svelte`) has two modes. **Audiobook** (`audiobook-player.svelte`, `data/audiobook.ts`): an audio file plus SRT/VTT subtitles, matched to the book by `matchCues` (`functions/audiobook/subtitles.ts`, exact match, then trigram voting), stored in IndexedDB (`audiobooks`; the playback position is in localStorage so the blob is never rewritten). **AI voice** (`tts-player.svelte`, `lib/data/tts.ts`) reads from the current position without furigana.
    Both send the line being read as character counts; `showReading` in `b/+page.svelte` draws it as the `ttu-reading` CSS highlight and scrolls/turns the page when it isn't visible.
    The AI voice calls ElevenLabs directly from the browser (`POST api.elevenlabs.io/v1/text-to-speech/<voice>/with-timestamps`, `xi-api-key`, model `elevenLabsModel$`, default `eleven_v4`) in chunks of 200-800 characters with `previous_text`/`next_text`. The character timestamps become a phrase timeline (`readingTimeline` in `data/tts.ts`) that drives the highlight. Audio is cached around the current chunk only (`data/tts-audio-cache.ts`).
  - Selecting text shows a toolbar (`book-reader/selection-toolbar.svelte`): four highlight colours, "Note", and "Ask AI" (`book-reader/ask-ai-panel.svelte`, `lib/data/ask-ai.ts`), which streams from OpenRouter chat completions and has preset buttons (Settings → AI).
  - Search (magnifying glass or Ctrl+F, `book-reader/book-search-panel.svelte`, `lib/functions/book-text/book-search.ts`) searches the rendered text, furigana excluded, and jumps by character count like a bookmark.
  - Highlights and notes (`lib/data/annotations.ts`, companion panel → Highlights) are anchored by character counts (`lib/functions/book-text/text-positions.ts`) and drawn with the CSS Custom Highlight API, so the book DOM is never modified.
    They are stored in IndexedDB (`ttu-annotations`, opened by `data/reader-db.ts`, which also holds recaps, lorebooks, audiobooks and kanji seen); the cache of a synced book records its owning account and is ignored under another sign-in state. Calibre books also sync them as `annotations.json` in the book's WebDAV folder (merged per highlight, newest edit wins, deletions kept as tombstones).
    `BookmarkManager.getRenderedStartCount()` gives the character count where the rendered DOM starts (the current section in paginated mode).
  - Manga (`lib/data/manga.ts`, reader `routes/m/+page.svelte`): CBZ/ZIP files load with `functions/file-loaders/cbz/load-cbz.ts` into an ordinary book record, so library, IndexedDB and sync are unchanged. The pages are the blobs; `elementHtml` is `<!--ttu-manga-->` plus the page names as JSON (`isManga`, `mangaPages`), `characters` is the page count, and the bookmark stores the page index as `exploredCharCount`. `/b` redirects manga to `/m`, which has none of the book extras. Reading mode (`mangaReadingMode$`, rtl/ltr/vertical) is per browser.
    The catalog lists CBZ and ZIP files that are mostly images (`manga_pages`/`is_valid_book` in `build-catalog.py`; ZIPs that wrap EPUBs are skipped), with the first page as `cover.jpg`. The import service queues `.zip` as `.cbz` (Calibre would unpack a `.zip`) and passes the file name as `--title`. The difficulty service ignores manga.
  - Visual novels (`lib/data/vn.ts`, player `routes/v/+page.svelte`): a ZIP holding an ONScripter script (`findVnRoot`: `0.txt`, `00.txt`, `nscript.dat`…) is loaded by `loadCbz` → `file-loaders/vn/load-vn.ts` into a book record like manga: the game files are the blobs (paths relative to the game folder), `elementHtml` is `<!--ttu-vn-->` plus `{encoding, files}` (`isVn`, `vnInfo`), `characters` the script's text (`scriptCharacters`). `/b` redirects them to `/v`.
    The engine is ONScripter-yuri (GPL-2.0) built to WebAssembly by `scripts/onsyuri/build.sh` (Docker, pinned commit + `text-hook.patch`) into `static/vn/onsyuri.{js,wasm}` (committed; rebuild only when the engine or patch changes). `static/vn/player.html`/`player.js` run it in a same-origin iframe outside SvelteKit's CSP; `startGame()` lazy-loads game files from blob URLs, mounts saves on IDBFS (`/save/<hash of title>`) and falls back to `static/vn/default.ttf` (Noto Sans JP).
    The patch calls `self.onsyuriText(bytes, skipped, boxes)` at every click wait with the current page's raw text (ruby as `(base/reading)`) and where `drawChar` drew each of its characters (byte offset, x, y, font size; ruby readings excluded). The page turns the boxes into screen lines (`overlayLines`) for `player.js`'s `showText`, which lays them as transparent text over the canvas for Yomitan (one absolutely positioned div per line, cleared on any click or key but modifiers; clicks on the text are re-dispatched to the canvas). It also decodes the text (`decodeText`) for the optional panel below the game (`parseVnPage`, `vnTextPanel`) and counts what was added (`newText`, page hashes in reader-db `vnRead` so rereads count nothing) for progress (`exploredCharCount`), statistics (`updateStatistic` from the tracker module) and kanji (`recordKanjiText`).
    Games can also be unpacked folders in `VN_PATH` (mounted at `/vn` in web, catalog and import; nginx `/calibre/vn/` with JSON listings, `VN_DIR` in `render-nginx.sh`): `vn_games` in `build-catalog.py` lists each folder (format `VN`, negative id from the name, `file` = the script's folder, cover relative to `VN_PATH`), the handler's `processCalibreBook` stores only `loadVnFolder`'s file list and script analysis (`VnInfo.base`, no blobs, no difficulty), and the player fetches files by URL.
    Calibre games' saves sync as `vnsaves.json` (personal, base64 per save file, newest wins, `mergeVnSaves`). The catalog lists CBZ/ZIPs with a script and marks them `vn` (not manga).
  - The reader companion (book icon, `book-reader/reader-companion.svelte`) holds Highlights, Story so far and Lorebook as tabs.
  - "Story so far" (`book-reader/recap-panel.svelte`, `lib/data/recap.ts`) summarises each finished chapter once (cached in IndexedDB), then writes a spoiler-free recap when asked (never automatically), saved with its position so earlier recaps can be reread. Companion tabs stay mounted once visited. After 7+ days away the reader offers it.
  - Lorebook (`book-reader/lorebook-panel.svelte`, `lib/data/lorebook.ts`): SillyTavern-style entries written by the recap model. `processedUpTo` records the character count read so far; updates only send the text after it (20k-character requests). `lorebookAutoInterval$` (Settings → AI) updates it in the background every N characters (`autoUpdateLorebook`, called 15 s after the position settles; waits 10 min after an error). Updates run in the module, not the panel (`stopLorebookUpdate`, progress and errors in `lorebookProgress$`), so they survive closing it. Exports SillyTavern World Info JSON; `copyLorebookTo` hands the entries to a later book of the series (`laterInSeries`, from the Calibre catalog).
  - All AI system prompts live in `lib/data/ai-prompts.ts` in English and Japanese, picked by `aiLanguage$` (EN | 日本語 toggle, `components/ai-language-toggle.svelte`); unchanged default presets show in Japanese too (`presetsForLanguage`).
  - API keys, the voice ID and speed, the OpenRouter models (Ask AI and recap), the Ask AI presets and "About you" note (`askAiReaderNote$`, appended to the Ask AI system prompt) are set in Settings → AI, which starts with a key setup guide (`ai-guide`, linked from the Ask AI panel when no key is set) (`settings/settings-ai.svelte`, `lib/data/ai-settings.ts`). They are stored in localStorage per browser and removed when the account signs out, expires or changes (`accountSettingsOwner`, `secretSettings` in `account-settings-sync.ts`). Keys must never reach shared files, URLs or error messages (`redactSecret`).
- Accounts (`lib/data/account.ts`, Settings → General → Account): the `account` service (`scripts/calibre/account/service.py`, standard library only) does username/password sign-in.
  Passwords are hashed with scrypt; failed sign-ins are throttled per username+address, per address, and per username after 50 (plus an nginx `limit_req`); sessions use a `__Host-` Secure/HttpOnly/SameSite=Strict cookie with idle and absolute expiry. The database is `state/account/accounts.db`.
  First start: on an empty database the service creates `admin` with a random temporary password (`ensure_initial_admin`, `state/account/initial-admin.json`, 0600), printed in its log, by `ebook-account initial-admin` and at the end of `deploy.sh` until that account signs in; it stays flagged `temporaryPassword` until its password changes.
  Updates (admin panel → Tools → Updates, `components/admin/update-tool.svelte`, `data/app-update.ts`): the browser compares `/version.txt` with `main` on GitHub (`UPDATE_REPO`); "Update" posts `admin/update`, which writes `state/update/request.json`; the host's `ebook-update` (systemd path unit, installed by `deploy.sh` via `ebook-update install`, which writes the `updater` marker) downloads the commit, swaps `/opt/ebook-reader`, builds, restarts and reports in `status.json`.
  There is no sign-up. Admins manage accounts in the admin panel (`routes/admin/+page.svelte`, Accounts tab = `settings/settings-admin.svelte`, `/account/api/admin/*`; linked from Settings → Account for admins and `difficulty` holders, `canOpenAdminPanel`), or with `ebook-account add NAME [--admin]`, `admin NAME on|off`, `permissions NAME a,b`, `passwd|remove NAME` and `list` in the account container. Signing in only works over HTTPS unless `ALLOW_HTTP_ACCOUNTS=1` (HTTP sessions use the non-Secure `ttu_session` cookie, honoured on HTTP requests only; the UI warns); the HTTP page links to `VITE_HTTPS_URL` (e.g. in a gitignored `apps/web/.env.local`) or the current host.
  Security (CHANGELOG "Security hardening"): sync folders are served as downloads only; book HTML goes through `parseBookHtml`/`sanitizeBookElement` (`file-loaders/utils/sanitize-book-html.ts`, inert document) at import and in `formatBookDataHtml`; `kit.csp` (hash mode) allows only the site's own scripts, so never add inline scripts or `on*=` attributes (put boot code in `static/`). Chrome logs `script-src-attr` violations when inert parsing meets `on*` attributes: harmless. Reads of the library, catalog and sync folder need an account, a trusted network or `PUBLIC_READS=1`; uploads stop below `MIN_FREE_MB`.
  Permissions (nginx `auth_request` → `auth/<permission>[/writes]`; `auth_status` in `service.py`): admins have all; others get `import`, `series`, `difficulty` (`users.permissions`, admin panel → User permissions). Calibre import, difficulty job POSTs and `series.json` writes need them (UI hidden via `hasPermission`); signed-out writes to `/calibre/sync/` only from `geo $trusted_network` (`TRUSTED_NETWORKS`). Behind a reverse proxy, set `REAL_IP_FROM`, or everyone looks like the proxy.
  nginx serves each account's own WebDAV folder at `/account/sync/` (`auth_request` to the service; files in `accounts/<account id>/`).
  While signed in, the Calibre handler puts per-reader files there: progress, statistics, reading goals (`isPersonalFile`), `annotations.json`, and `recaps.json`/`lorebook.json` (`data/extras-sync.ts`: recaps merged per chapter/saved recap with deletion records, lorebook newest-wins by `modified`). Book data and covers stay in the shared `/calibre/sync/`.
  The Statistics page and Home dashboard pull every book's statistics from there (`data/statistics-sync.ts`, own handler instances so they never switch the reader's context).
  AI settings and themes sync through `settings.json` in that folder (`lib/data/account-settings-sync.ts`; add a store to `sharedSettings` to sync it). Each setting keeps its own last-changed time, and the newest wins.
  Settings → Reader options (`readerSettings`) sync per reader profile, stored as `reader.<phone|desktop>.<key>`, so phones and larger screens keep separate reader styles (e.g. 1 vs 2 page columns). A device is a phone if it has a coarse pointer and a screen short side under 600 px (`readerProfile()`).
  `POST /account/api/import-shared` copies progress, statistics and highlights saved while signed out into the account (never overwriting its own files); the UI no longer offers it.
- Settings page (`routes/settings/+page.svelte`): sidebar areas and sections (collapsible groups, scroll-spy; on phones a list that drills into one area), defined in `settings/settings-sections.ts`. URLs are `/settings?section=<area>#<section id>`; old `?tab=` links still work. The first jump to the section in the URL doesn't call SvelteKit's `replaceState` (the router isn't ready in the first `onMount`).
  Each `SettingsSection` (by id) can live in any component; CSS `order` keeps the sidebar order. Search (Ctrl+F) matches `SettingsItemGroup` titles and descriptions (`data-settings-search`).
- The reading tracker starts when a book opens if statistics are enabled and `trackerStartOnOpen$` is on (`startTrackerOnOpen$` in `b/+page.svelte`, after 1.5 s without a page change).
- Themes can follow the system's light/dark mode (`followSystemTheme$`, `darkTheme$`, `selectTheme()` in `theme-store.ts`).
- Library select mode has "Clear progress" (`lib/functions/clear-reading-progress.ts`): it saves a new bookmark at the start rather than deleting the progress file, so devices with an older cached position adopt the reset.
- Library Home/Store tabs (`lib/data/library-home.ts`): Home has the learner dashboard (`book-card/learner-dashboard.svelte`: totals from upstream statistics via `data/learner-stats.ts`, number of different kanji met from `data/kanji-seen.ts`, recorded by the reader per browser), Continue reading and "My books" (`homeBookTitles$`, titles, synced in `sharedSettings`). The Store is the full list, as Books or Series (`storeView$`, `series-grid.svelte`, first book's cover; opens the `series:<name>` filter, listed in reading order by `orderSeries`: Calibre index if distinct, else the volume number in the title); its search shows matching series with "Add all" (`series-results.svelte`).
- Library clicks: in the Store a click selects a book (open it with "Read" in the select toolbar); on Home a click opens it and a long press or right-click selects it (`functions/use-long-press.ts`).
- Library extras: a "Continue reading" shelf, series/difficulty columns and sorting (`book-card/library-sort.ts`), and filters for difficulty, series and Calibre tags (`book-card/library-filters.ts`).
- Difficulty estimates (admin panel → Tools, or the gauge button for selected books in the library's Calibre source, shown to everyone, estimating needs `difficulty`; `book-card/difficulty-panel.svelte`; on demand only; `difficulty` profile) use Jiten's features (https://github.com/Sirush/Jiten, Apache-2.0) and our own model, chimi-difficulty, trained on jiten.moe's own scores.
  The `difficulty` service (`scripts/calibre/jiten/`, venv `/opt/venv` in the image, state in `state/difficulty/`, `DIFFICULTY_WORKERS` workers of about 0.5 GB) scores books and serves the results as `/calibre/difficulty.json`. Restarting it stops a running job.
  Word frequencies come from Jiten's Yomitan frequency list (`state/difficulty/frequency-dictionary.zip`, from `jiten_freq_global.zip` on jiten.moe/frequency-dictionaries; uploadable from the panel when missing, `POST dictionary`, checked by `install_dictionary`); there is no frequency table built from the library any more.
  The model, chimi-difficulty (`jiten/chimi-difficulty.onnx`, built by `jiten/distil/`, README there), is Jiten's 55 features plus `EXTRA_FEATURES` (`features.py`: log characters and unique kanji, coverage ranks, MATTR, 連体形+noun relative clauses and predicates per sentence, hiragana share, non-常用 kanji, ruby), trained on jiten.moe's algorithmic scores; `-low`/`-high` models give the 10-90% range (widened by `chimi-difficulty-range.json`) (`low`/`high` in the results), `words95` the common words for 95% coverage. Word origins come from `goshu.json.gz` (UniDic), kanji grades from `kanji-grades.json` (KANJIDIC2), both built by `distil/make_tables.py`. Estimates carry `model` (`MODEL_VERSION`); "Books without an estimate" redoes those made by another model.
  Each estimate also writes the book's kanji counts (`state/difficulty/kanji/<id>.json.gz`, `GET /calibre/difficulty/api/kanji/<id>`); the library's gauge (all readers; estimating needs `difficulty`) compares them with `kanji-seen` (`kanjiCoverage`). `distil/validate_speed.py` checks estimates against readers' reading speed once there are enough statistics.
  jiten.moe itself scores with a private sentence-level model on RunPod (`DifficultyComputationJob` in Jiten's repo); the public `.onnx` is unused there.
  Jiten's API is for personal projects and small-scale research only (jiten.moe/guides/api-and-scraping): the training data was one list request plus one request per matched series, at most 75 a minute. Don't call it from the app or the service.
- Themes (`lib/data/theme/`, Settings → Themes, guide in `themes.md`) colour the whole app, not just the book: `theme-tokens.ts` lists every colour and its CSS variable, `themes.ts` the built-ins, inheritance and import validation, `theme-style.svelte` applies the active theme to `<html>`.
  Use the CSS variables (e.g. `var(--surface-strong-color)`, `var(--reader-panel-bg)`) rather than fixed colours in components.
- Visual design "Washi & Sumi": the default themes `washi-theme`/`washi-dark-theme` (`defaultLightThemeId`/`defaultDarkThemeId`), mincho display font `--app-font-display` (KZ UDMincho). Every page and the reader use the shared `app-header` (flat bar; bottom tab bar on phones except in the reader). Settings rows are `SettingsItemGroup` (label left, control right; `wide` stacks); on/off `ButtonToggleGroup`s render as a switch, others as a segmented control, named by the row via context. Shared control styles are `.app-input`, `.app-button` (+ `-primary`/`-quiet`/`-danger`), `.app-switch` in `app.scss` (`inputClasses`/`buttonClasses` in `css-classes.ts`). Components use theme colours only: CSS variables or the Tailwind colours mapped to them in `tailwind.config.cjs` (`text-danger`, `bg-overlay`…), never palette classes. `themes.test.ts` checks every built-in theme for WCAG AA.

## Commands and tests

- Front end (Node 24, pnpm 10 from `packageManager`): `pnpm test` (Vitest + jsdom, `src/**/*.test.ts`) and `pnpm check` (svelte-check) in `apps/web`, `npx eslint .` from the repo root. Without Node installed, run them in a `node:24-slim` container (CONTRIBUTING.md).
- Python tests: `python3 -m unittest discover -s scripts/calibre/tests` (standard library only).
- Baseline: tests all pass, ESLint is clean, `pnpm check` has 30 pre-existing errors. Keep it that way.
- When dependencies change, regenerate `pnpm-lock.yaml` with pnpm 10 (`pnpm install --no-frozen-lockfile`; `CI=true` forces frozen mode); image builds use `--frozen-lockfile`.
- Svelte compiles with `immutable: true` (upstream `svelte.config.js`): assign new objects/arrays/Sets, never mutate and reassign the same one, or nothing re-renders.
- Test patterns: component tests mount with `new Component({ target, props })` (Vitest uses Svelte's browser build, see `reader-companion.test.ts`), `fake-indexeddb/auto` for IndexedDB, `vi.stubGlobal('fetch', …)`, `vi.mock('$lib/data/account', …)` for signed-in state. Storage handlers import each other in a cycle: import `storage-handler-factory` first or mock `calibre-handler`. Components that pull in `account-settings-sync` need it mocked (`settings-account.test.ts`).
- CI (`.github/workflows/ci.yml`): ESLint, `pnpm test`, build, Python tests, compose check and all four image builds. Releases (`release.yml`): tag `v*` → images for amd64/arm64 on GHCR, used via `IMAGE_PREFIX`/`IMAGE_TAG`. The web image builds its Node stage on `$BUILDPLATFORM` (static output), so arm64 needs no emulation there.
- Docs: README.md (overview), docs/INSTALL.md and docs/CONFIGURATION.md (running it), ARCHITECTURE.md (design, data flow, tech debt), CONTRIBUTING.md (conventions, how to add things), docs/QA.md (manual test plan), CHANGELOG.md (add an entry for user- or server-visible changes).

## Fragile areas

- `routes/b/+page.svelte`: huge; the reader extras' glue lives inline. Keep new logic in `lib/` modules with tests and verify with a real book in both view modes.
- Sync file names carry metadata (`bookdata_*`, `progress_*`, upstream's `BaseStorageHandler`); renaming or adding prefixes affects every device. Per-reader prefixes must match `isPersonalFile` and `PERSONAL_PREFIXES` in `account/service.py`.
- Book titles are identities (folder names). Changing how `build-catalog.py` makes titles unique orphans synced data.
- `scripts/deploy.sh`: the server-side steps are single-quoted `bash -c '…'` strings run through `run`; a single quote inside one ends it early. Over SSH they are re-quoted with `printf %q`, so keep them plain bash.
- `local/` and `CLAUDE.local.md` are gitignored and hold one deployment's settings; never commit them.
- The nginx template is rendered with `envsubst` limited to its own `${…}` names (`render-nginx.sh`); new placeholders must be added to that list, and nginx's own `$variables` must stay unbraced or unlisted.

## Verifying changes

After deploying, check that the pages load (`/`, `/manage`, `/settings`, `/version.txt`) over HTTP and HTTPS, and that `/version.txt` shows the commit.
`pnpm check` has pre-existing errors (e.g. `PasswordCredential`, `on:swipe`); only new ones matter.
Restarting the stack stops a running difficulty job: check `/calibre/difficulty/api/status` first.
For UI changes, verify the relevant route in a browser if possible. Reader changes need an actual book loaded, which is stored per browser.
